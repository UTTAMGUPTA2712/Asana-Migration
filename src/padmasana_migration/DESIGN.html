How we build the seed data, in three scripts

A plain-language walkthrough of the pipeline: upload the attachments, build the people/teams/boards, then build the tasks — complete with comments and activity, run in parallel — all before anything touches a real database.

Draft — no code yet

Where this lives

A second package, same repo

padmasana_migration is a new top-level package under src/, right next to the existing asana_migration — not a separate project. One repo, one pyproject.toml, one uv sync. The two packages just don't import from each other: asana_migration only ever talks to Asana, padmasana_migration only ever reads what it already exported.

asana-migration/ data/ ← Asana export, read-only from here on build/ ← everything the 3 scripts below produce (gitignored, like data/ and var/) src/ asana_migration/ ← existing: Asana → data/ padmasana_migration/ ← this package: data/ → build/

Ground rules

Before any of the three scripts

Two rules that shape everything below.

  • Never touch data/. Every script below only reads from it. Everything it produces goes into a brand-new folder, build/, at the same level as data/ and var/. Get something wrong? Delete build/ and run the script again — re-downloading the Asana export is the thing we actually can't redo, not re-running our own script.
  • Nothing here writes to a real database. These three scripts only produce finished JSON files in build/. Actually loading that into padmasana happens later, as its own separate step — see the end of this page.

Overview

The three scripts, in order

1 upload_attachments.py
Uploads every attachment file to the file-service, one at a time. Needs the network.
→
2 build_teams_and_boards.py
Users, teams, boards — small enough to build entirely in memory. No network.
→
3 build_tasks.py
Tasks and everything attached to them — the big one, goes task by task. No network.

Each one is its own command you run separately, and each is safe to stop and re-run — the same idea as asana-migration's split between import-all and download-attachments.

Running 1 and 3 in parallel

Reusing what import-all already built

Scripts 1 and 3 both process thousands of small, independent jobs — one attachment, one task. asana_migration already solved exactly this shape for its own import, so we reuse it instead of writing it twice.

  • JobQueue (from asana_migration.jobs) — a persistent, resumable, crash-safe queue backed by one JSON file.
  • WorkerPool (from asana_migration.worker) — a pool of threads draining that queue, exactly how download-attachments already runs its uploads concurrently today.
The one thing that has to change

asana_migration's own queue already lives at var/jobs.json — this project must never point at that file, or the two tools' progress tracking would collide. JobQueue already takes a path argument for exactly this reason, so padmasana_migration gives it its own: var/padmasana_jobs.json, right next to it, never shared.

Worker count is sized directly by a --concurrency flag, the same way download-attachments does it — there's no Asana call to pace here, just file-service uploads (script 1) and local JSON building (script 3). Script 2 stays single-threaded; its data is small enough that parallelizing it would only add complexity.

Script 1

upload_attachments.py

Goes through every task's attachments, uploading one per job — --concurrency N of them in flight at once — and gives each one a real home in padmasana's file-service.

  1. Real file? (host: "asana", already downloaded to local_path) — upload it to the file-service and get back its new id/url.
  2. Link only? (gdrive / external) — there's nothing to upload, so it's just carried over as-is.
  3. Either way — write the result into a new file under build/, same shape as the original attachments.json, plus the new file-service id/url and anything else padmasana's attachment table needs. The original in data/ is never edited.
Resumable

Before queuing a job, the script checks whether build/ already has a result for that attachment. If it does, it skips it — so stopping halfway through a huge upload and starting again never re-uploads what's already done, even with several worker threads running at once.

Script 2

build_teams_and_boards.py

Everything here is small next to the task data, so this script just builds it all in memory and writes it out at the end — no streaming needed.

A. Users — match padmasana's own shape

padmasana already has a way to bring people in: its own import-users command, which pulls everyone from Firebase and reshapes them into one flat record — user_reference_code, email, name, last_name, profile_url, workspace — the exact shape every table that stores a person expects.

So instead of inventing our own user shape, we match Asana's {gid, email, name} to that same shape, joined on email. The people we build end up looking exactly like ones the app already knows how to handle, not something foreign bolted on.

Script 3

build_tasks.py

The big one. Rather than holding everything in memory, it walks the export task by task (including subtasks) — one job per task on the same job queue as script 1, its own --concurrency.

The subtask problem

A task can be a subtask of another task — but we don't process tasks in any order that guarantees a parent comes before its children. If we tried to set the parent link while building each task, we could easily point at a task that doesn't exist yet.

The fix: two passes

Pass 1 — create every task

Every task is written with no parent set at all. Order doesn't matter, because nothing points at anything yet — nothing can break.

Design homepage ↳ Pick colors ↳ Export assets

Pass 2 — link parents

Now that every task already exists, go back and fill in each task's parent. Every parent it could ever point at is already there.

Design homepage ↳ Pick colors ↳ Export assets

Alongside each task

The same pass that builds a task also builds what hangs off it: assignee, tags, which section it sits in, collaborators, and attachments (the attachments step doesn't upload anything itself — it just looks up the file-service id/url that script 1 already produced). Comments and activity are built too, completely, matched to how padmasana itself records them.

Comments and activity — built together, the way padmasana does it

padmasana doesn't treat "the comment feed" and "the activity feed" as two things bolted together — a comment is one of a fixed set of event types the activity log understands. Reading the real code: task_activity_log only ever stores one of 13 fixed event types, each with its own small, specific data payload — not a freeform log.

padmasana event typedata it storesWhere it comes from
TASK_CREATEDnoneSynthesized once per task, from its own created_at
TASK_COMPLETED / TASK_IN_COMPLETEDnoneAsana story marked_complete / marked_incomplete
TASK_ASSIGNEDassigneeAsana story assigned
TASK_UNASSIGNEDprev_assigneeAsana story unassigned
TASK_RENAMEDold_value, new_valueAsana story name_changed — best-effort, Asana's text doesn't always give both values cleanly
TASK_DESCRIPTION_ADDED / _UPDATEDvalue / old_value+new_valueAsana story notes_changed — same best-effort caveat
TASK_DUE_DATE_UPDATEDdue_dateAsana story due_date_changed
TASK_ADDED_TO_BOARD / _REMOVED_FROM_BOARDboard_nameAsana story added_to_project / removed_from_project
TASK_MOVED_TO_SECTIONprevious_section, current_section, board_nameAsana story section_changed — section names parsed from story text, best-effort
TASK_COMMENT_ADDEDcomment_uuidEvery comment we build gets exactly one of these — not read from stories.json

Comments specifically: each entry in comments.json becomes a task_collaboration.comment row and one TASK_COMMENT_ADDED activity row referencing its uuid — that pairing is exactly what padmasana's own comment code does (it reads the activity row, then fetches the real comment by that comment_uuid to fill in the content). Asana's stories.json also has its own comment_added entries duplicating the same events — skipped in favor of comments.json, the cleaner, purpose-built source.

Not everything maps

Subtask-added notices (redundant anyway — that relationship is already captured via parent, see the two-pass fix above), attachment-added notices, reactions, custom fields, tags, dependencies, mentions, rule automations, and a handful of other Asana-only story types have no padmasana event type to map onto, so they're left out rather than force-fit. Checked against this export: excluding comment_added (fully covered via comments.json instead), close to 30% of the remaining story entries fall into this "no mapping" bucket. The activity tab in padmasana will still be a genuine, complete history — just told entirely in padmasana's own vocabulary, not Asana's.

Deliberately left out, for now

What these scripts don't build

  • Nothing goes into padmasana's notification tables — we don't want real people notified about years-old Asana activity.
  • No real-time events get fired — this is a one-time backfill, not live usage.

After build/ is done

Loading it into padmasana — a separate, later step

Once all three scripts have run, build/ holds everything padmasana needs, fully formed — nothing left to compute.

Next phase, not now

Write small seed scripts inside padmasana-service itself — it already has this exact pattern (seed:run, its MikroORM seeders). Copy the finished build/ folder into that repo, and let a seeder there read the JSON and save it using padmasana's own code, so its normal checks and relationships still apply.
